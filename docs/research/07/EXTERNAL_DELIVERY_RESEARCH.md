# Task 07 — Deferred external-delivery research

Checked 2026-10-25. **Not selected for the hackathon demo and not implementation authorization.** The human chose a banner inside the open website and explicitly deferred delivery after closure. See the [current implementation specification](../../implementation/07_SCHEDULED_REMINDERS_IMPLEMENTATION.md) for the actual narrowed contract. No accounts, secrets, sends, recipient registration, setup, deployment or purchases were used to perform this research.

This note preserves the facts investigated before the human clarified scope. It is not a ready-to-code external reminder plan. If external delivery is resumed, the human must choose the one channel, sender/operator identity, recipient opt-in, runtime/storage, budget and exact delivery expectation. Do not silently select the researched email provider or treat a local banner as Web Push.

## Operational options investigated

| Option | Honest boundary | Additional work and unresolved commitments |
| --- | --- | --- |
| Local persistent app service | Browser can close while an awake, networked local Node server keeps running. A due-work scan shares the app's one serialized persistence owner; no independent process writes its JSON file. | Startup scheduler, durable outbox and exclusive data-directory ownership before any load/migration/write; supervised startup/recovery and host operation. The user selected local operation as permissible, but did not authorize this expanded delivery feature. |
| Hosted Cloudflare scheduled Worker + D1 | Can run when the owner's computer is off after authenticated reminder metadata reaches hosted storage. | Account, deployment, credentials, durable metadata, authenticated update/cancel/opt-out route and operational owner. A hosted worker cannot access local localhost or discover edits stored only on the owner's disk. Offline unsynchronized cancellation/rescheduling needs a separately agreed contract. Not selected. |
| Web Push as a channel | A server sends through a push service to an authorized subscription; an inactive page can receive a service-worker event on a supported device. | Browser permission, subscription/private endpoint handling, application-server keys, supported browser/device tests, scheduler and persistent intent state. A banner requires none of these. Not selected. |

The [Next.js instrumentation guide](https://nextjs.org/docs/app/guides/instrumentation) says `register` runs once per new server instance. That can bootstrap a Node-only loop in a future local service, but is **not** a cross-process singleton or a guarantee that a hosted function remains running. [Node timers](https://nodejs.org/api/timers.html) do not guarantee exact callback timing; very large timeout delays are unsuitable for a long-range calendar. Proposed implication: periodic nonoverlapping scans of durable `due <= now` records, with startup catch-up and a visible last-scan time.

[Cloudflare Cron](https://developers.cloudflare.com/workers/configuration/cron-triggers/) runs schedules in UTC; configuration changes can take up to 15 minutes to propagate. The opened documentation does not establish exact-time, exactly-once or missed-run catch-up guarantees. The [scheduled handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/) needs explicit local test triggering. These facts favor overdue-record scans with idempotency rather than treating cron invocations as reminders themselves.

[D1 `batch`](https://developers.cloudflare.com/d1/worker-api/d1-database/) provides transactional sequential SQL batches with rollback on failure. A database transaction still cannot atomically include an external delivery API. [Cloudflare Queues](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) provides at-least-once delivery, so duplicate messages remain possible. Its [retry/delay behavior](https://developers.cloudflare.com/queues/configuration/batching-retries/) and [dead-letter queues](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/) need deliberate configuration; maximum delay is 24 hours. Queues is an optional ready-work transport, not a required long-range reminder store.

## Email evidence investigated; email was not chosen

[Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys) retains send keys for 24 hours. Identical retries reuse the result; changed payload under one key is rejected, and concurrent in-progress requests can conflict. A stable dispatch key and immutable payload must be persisted before network I/O. Proposed safety rule: bound automatic retries to the valid idempotency window; unresolved ambiguity after that window stops for reconciliation instead of sending under a fresh key. This is an engineering proposal, not an exactly-once guarantee.

[Resend event definitions](https://resend.com/docs/webhooks/event-types) distinguish a successful request/`email.sent`, which begins attempted delivery, from `email.delivered`, meaning acceptance by the recipient's mail server. Neither proves inbox placement or that a human read it. Retain accepted, delivered-to-server, delayed, bounced/failed, suppressed and unknown evidence without a generic “delivered” success label.

[Webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests) requires the raw body, signing secret and Svix headers. Validate signature/timestamp and deduplicate event identities before durable updates. [Webhook retries/replays](https://resend.com/docs/webhooks/retries-and-replays) can repeat events and disable repeatedly failing endpoints. Local-only operation cannot receive provider callbacks at an unreachable loopback URL. A future local branch could poll [retrieve sent email](https://resend.com/docs/api-reference/emails/retrieve-email) by retained provider ID and interpret its `last_event`; failure to obtain evidence remains unknown. Polling does not prove personal receipt.

[Resend verified domains](https://resend.com/docs/dashboard/domains/introduction) requires an owned verified sender domain for general sending. The [shared resend.dev restriction](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain) permits testing to the account owner's email only. Domain/DNS access, sender identity, consented recipient and provider credentials are future prerequisites, not known account facts. A testing exception does not authorize use or prove a production sender is configured.

## External state machine and recovery requirements, if resumed

This is a transport-independent checklist of gaps, not a selected platform implementation. It avoids losing the failure analysis and must be revised for the chosen channel.

- Persist an outbox intent with workspace/target temporal generation, recipient/subscription generation, opt-in revision, trigger instant, expiry/catch-up policy, immutable bounded payload/hash, stable dispatch ID and provider key. Unique occurrence/recipient/channel generation prevents duplicate intents.
- Keep `pending`, `dispatching`, `retryScheduled`, `providerAccepted`, `outcomeUnknown`, `failed`, `cancelled` and `expired` distinct. Delivery evidence is separate and channel-specific; never equate acceptance with a user's receipt.
- Claim work transactionally with a fencing token/attempt identity and short lease. Use the same persistence owner for local JSON or a transactional durable store for concurrent hosted workers. Network calls run outside database/repository transactions; commit their results only against the matching intent/attempt.
- Recheck current opt-in, target generation, completion, pause and expiry immediately before dispatch authorization. Withdrawal committed before authorization prevents dispatch. After the call starts, cancellation cannot recall it; show “already in progress / outcome unknown” rather than promise no message can arrive.
- Deadline edits invalidate pending generations, preserve old attempt/key history and create a new generation. Do not rewrite already accepted payload/history. Reset and source re-extraction must retain uncertain sends and prevent ID reuse from reviving old work.
- Propose bounded transient retries (for example at most 4 send attempts over less than the provider key lifetime), honor Retry-After within the overall expiry, classify permanent auth/address/subscription failures, and expose operator reconciliation. Exact retry/TTL values depend on the human-selected channel. Ambiguous timeout/crash never becomes success or an unbounded new-key retry.
- Startup reconciles interrupted dispatches; duplicate scheduler/queue events are normal inputs. Replayed or out-of-order delivery evidence cannot regress a proven state. Acknowledgement of seeing a notification is not equivalent to reading or acting on its contents.
- Pause/unsubscribe must be enforced in the worker's durable authority, not merely hidden in the UI. An unavailable local server cannot offer off-device unsubscribe; hosted unsubscribe needs a narrow signed/revocable capability and explicit confirmation semantics. No local management link may imply it works from another device. Choose that boundary with the human before shipping external delivery.

For actual Web Push, the [W3C Push API editor's draft](https://w3c.github.io/push-api/) and [RFC 8030](https://www.rfc-editor.org/rfc/rfc8030.html) describe subscription/service delivery and time-to-live semantics. Draft-only features are not assumed implemented. A push-service acceptance response is not evidence that an OS notification was displayed or read. Revoked/expired subscriptions must stop future dispatch and secrets/endpoints must remain private. [WebKit's iOS/iPadOS guidance](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) describes Home Screen installation and permission after direct interaction. These setup/testing costs support the human's narrower banner demo choice, without claiming universal browser behavior from one vendor's documentation.

If resumed, test synthetic duplicate ticks, claim races, crash-before/after provider acceptance, timeout ambiguity, idempotency expiry, deadline edit versus dispatch, opt-out/pause during retries, DST/timezone boundaries, unknown/date-only inputs, provider outage/quota, replayed evidence, restart recovery and identity/subscription replacement. Default tests remain offline with mocked transports and isolated state. A live demonstration requires explicit intent, an opted-in owner/device, working infrastructure and honest accepted-versus-observed evidence; none was performed here.
