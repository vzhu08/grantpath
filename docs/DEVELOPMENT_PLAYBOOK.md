# Using the kit at kickoff

For this project, apply [PROJECT_BRIEF.md](PROJECT_BRIEF.md) and `../AGENTS.md` first: GrantPath is a time-constrained hackathon build pursuing technical impressiveness, clarity, impact and novelty. Keep the critical judge path and distinctive working mechanism ahead of optional feature breadth. Reserve integration and rehearsal time. The 24-hour schedule below is a reusable example, not this project's confirmed event clock or deployment authorization; current local-only scope and task ownership remain authoritative.

Use the [human–AI team workflow](HUMAN_AI_TEAM_WORKFLOW.md) to assign human accountability and approval owners, follow the 24-hour checkpoints, and report evidence and actionable blockers. It supports manual coordination; optional orchestration and existing technical controls remain unchanged.

Read event requirements and deadline, define the judge path and one distinctive capability, and fill the project brief/scorecard. Search the catalog, inspect minimal contracts/fixtures, choose the smallest dependency closure, generate or plan adoption, configure only required environment names, run doctor/checks, assign ownership and authorize a deployed skeleton. Do not equate this toolkit's longer build with the event's deadline.

| Event time in a 24-hour example | Observable milestone                                             |
| ------------------------------- | ---------------------------------------------------------------- |
| 0–1 h                           | Demo story, contract, ownership, deployed skeleton               |
| 1–4 h                           | Real input to real result end to end                             |
| 4–8 h                           | Deployed evidence of the distinctive capability                  |
| 8–16 h                          | Improve technical quality, usefulness and evaluation             |
| 16–18 h                         | Cut weak scope and converge on the judge path                    |
| 18–22 h                         | Freeze architecture, polish failure handling and reliability     |
| 22–24 h                         | Freeze features, rehearse, backup, verify and submit with buffer |

Scale to the actual deadline. Hold a brief working demo checkpoint every 60–90 minutes; inspect quality and latency and replenish a small Ready queue. If the core path fails at hour four, narrow scope at its failing boundary rather than adding features.

## Extend a prebuilt capability

Read its contract, fixtures, provenance and known limits. Claim a narrow module or consumer scope. Coordinate contract/dependency/migration changes with the steward. Preserve original source revision and record customizations in kit.project.json plus integration notes. Run the module and consumer checks and the exact UI path. Keep fake/live/replayed output visibly labeled.

## Frontend and backend together

Agree the wire schema and error/empty fixtures first. Product/UX owns pages and selected components, Platform/API owns named route files, Core owns selected modules. Import shared fixtures into bounded tasks. The API validates both request and response; the browser validates data before rendering. Integrate a real result early, then improve independent pieces.

## Before merging

Check scope and current-main compatibility; regenerate manifest-derived catalog/schema; inspect generated output and selected dependency closure; verify internal documentation links and affected standalone examples; record actual tests and live skips. Fix broken demo paths before dependent work. Use one queue and distinguish Merged from Verified.

## Demo and recovery

Keep a known-good deployed SHA and a permitted backup recording. Never present cached, manually prepared or prerecorded output as live. Validate the final judge path in a fresh session and verify submission receipt/status. A provider outage gets bounded retries and an explicitly labeled fallback; it does not justify fabricated evidence.

After the event, record waiting, ownership conflicts, weak tests and useful reusable code. Promote improvements back into modules with provenance and generic contracts. Preserve the source playbook retained in the original toolkit as background; [collaboration](COLLABORATION.md) is the actionable canonical companion.
